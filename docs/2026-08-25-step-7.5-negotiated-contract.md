# Step 7.5 — a negotiated contract boundary, because step 8 is HELD

**graph-senior-dev, 2026-08-25: step 8 is BLOCKED.** Deleting `degraded` and
`operationallyDegraded` is still approved as a target and still refused as an act, for a reason that
is not the one that blocked it before.

## Why it is held

The fail-closed guard the whole migration rests on has no consumer.

    canInterpretEvidence        production callers : 0   (definition + its own tests only)
    DEPRECATED_EVIDENCE_FIELDS  production callers : 0
    contractVersion across all 17 shipped skills   : 0 occurrences
    any published reader protocol                  : none

    POSITIVE CONTROL, same pass:
    evidenceContractStamp       production callers : 4   (code_intel_live.js:18,122
                                                          code_intel_hierarchy.js:34,328)

The control matters: the same search that returns 0 for the consumer returns 4 for the producer, so
the zero is a fact about the code and not about the instrument.

⇒ **The producer is wired; the reader does not exist.** Every evidence object carries
`contractVersion: 1`, nothing reads it, and no skill or document has ever told an agent to. Dev's
step-8 precondition — *"an old-reader hostile test proving an unknown schema REFUSES rather than
reading a missing boolean as healthy"* — is satisfied on paper by a passing test, over a mechanism
no live path invokes. Cutting the fields now recreates the exact `!undefined === true` hazard he
refused the quick deletion over, this time under a green suite.

⛔ **Third commission of this shape.** The doc layer had good precision and zero consumers for
weeks. Verified edges went 19 → 3008 table-side while the consumer side stayed 0 of 27. Here I
found an unconsumed guard and *hardened* it instead of asking who calls it.

## ⭐ And "add an internal caller" is NOT the fix

My first proposal was to wire at least one internal reader so the guard runs on a live path. Dev
refused it, correctly:

> *"Adding a producer-side adapter that stamps v2 and immediately calls its own v2 guard proves only
> self-consistency. It does not make an old external reader inspect the version."*

The hazardous consumer is outside the producer boundary — an MCP client or agent reading the
response. An internal caller would have produced a non-zero call count, which is the metric I was
reaching for, and no protection at all. **A call count is not a consumer, the same way a stamped
field is not a protocol.**

## The design

An explicit request capability on both affected verbs, so the consumer proves it understands v2
before receiving v2:

    acceptEvidenceContractVersion: 1 | 2

    omitted or 1             ->  contract 1, deprecated booleans present
    2                        ->  contract 2, both booleans absent
    malformed / 0 / negative
      / future / string      ->  typed REFUSE, no best-effort payload
    every response echoes the exact contractVersion selected

This is mechanically stronger than publishing prose, and it does not depend on old clients noticing
that a field appeared.

## Acceptance gate — dev's seven controls, treated as a gate and not as advice

1. old/default request receives v1 **and** the booleans
2. explicit v2 request receives v2 and **neither** boolean
3. a v1 reader against v2 refuses **through the real request/response path**, not through a unit
   test of the predicate in isolation
4. `0`, negative, future, and string versions refuse
5. both verbs share **one** negotiation owner and cannot drift
6. shipped skills document the request, and branch only on `exhaustive === true`, with `cause` for
   diagnosis
7. telemetry measures **actual v2 requests** before any default flip

⚠ **Control 7 is the one that would have been skipped**, and it is the one every adoption
measurement on this project argues for. 17 skills installed, 9 invocations ever, 12 never invoked
once, 0 from 1,059 subagent transcripts. Flipping the default on an assumption that clients adopted
v2 would be wrong by about the margin we have been wrong every previous time we assumed adoption.

Only after measured v2 adoption and a declared breaking release may the default move to v2. Existing
tool names retain v1 compatibility until then; the fields are not deleted globally merely because v2
exists.

## Accepted alternative

If the request surface is judged too large: keep the deprecated v1 fields indefinitely on the
existing tools and introduce versioned v2 tool/response endpoints instead.

**Not acceptable either way:** same-tool silent removal behind an unused exported guard.

## What did land

The localized defect dev found while checking the tripwire, repaired and accepted:
`canInterpretEvidence` accepted `0`, `-1` and `MIN_SAFE_INTEGER` as interpretable contracts, because
`seen <= understood` treats a version as an ordering rather than an identity. Now
`Number.isInteger(v) && v >= 1` on both arguments.

⛔ The test beside it had been **certifying** that fail-open — `toEqual([1, 0, -1])` under a comment
reading *"only real integers at or below the understood version"*. The comment stated the correct
rule while the assertion pinned the broken one.

⚠ `understood` of 0 and -1 were already refused before the repair, but incidentally — `1 <= 0` is
false — not by any validity check. The explicit predicate now pins the mechanism rather than the
outcome by accident.
