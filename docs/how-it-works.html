aify-project-graph · v0.1.0

A code map your AI agent can trust.

It reads your codebase into a graph, then layers a real language server's ground truth on top — clangd for C++, typescript-language-server for TS/JS, pyright for Python — and exposes both to coding agents (Claude Code, Hermes, Codex) as a small set of MCP tools plus a live dashboard.

Built C++-first for game engines (Sand Castle, Echoes of the Fallen / Tesseract) and since extended to TypeScript/JavaScript and Python behind the same evidence contract, it merges proven ideas from four similar open-source projects into one coherent system. The whole point: an agent should never be told "no callers / safe to delete" unless that's actually proven.

1What is it, in one minute

Coding agents are great at writing code but bad at knowing a large codebase — they grep, read the wrong file, and worst of all they hallucinate ("just delete foo(), nothing calls it" — when something does). This project gives the agent a reliable map and, crucially, tells it how much to trust each answer.

🗺️ A graph of your code

Every file, function, class, call, import, and inheritance edge — extracted with tree-sitter across many languages. Always available, instant, no toolchain needed.

🎯 Compiler ground truth

It drives a real language server — clangd (C++), typescript-language-server (TS/JS), or pyright (Python), picked by file extension — to resolve who actually calls a function across files, and marks those edges [lsp✓] as verified. Servers ship bundled; the host needs no LSP setup.

🛡️ An honesty contract

Every answer says where it came from. A "no callers" result is only trustworthy when it's proven exhaustive; otherwise the tool says so out loud.

2How it works — the layered architecture

Think of it as an escalation ladder. The bottom is always-on and cheap; each layer up adds precision where it matters. Everything writes into one graph, so a static query and a compiler-verified query live side by side.

3The trust model — the heart of it

Every edge carries a provenance tag, and every answer carries a trust banner. This is what separates this tool from "a graph with features": the agent always knows whether it can act on an answer or must verify first.

The one rule that defines the product: a tool may only claim "no callers / safe to delete" when it has proven exhaustive evidence (a ready language-server index that actually resolved that symbol — and that the language can prove it: never for Python). Otherwise it must say "absence is from the heuristic graph and is NOT exhaustive — verify with code_intel_references / rg."  Live testing on the real games caught several places where this slipped (a foreign/unity compile DB and a cold index both silently under-reported); all are fixed and regression-tested. A stale index or an unbuilt overlay also announces itself loudly, so "not found" never gets misread as "doesn't exist."

4The semantic layer — meaning, not just structure

The graph knows the shape of the code (who calls whom). This newer layer adds a sense of purpose: what each cluster is for, a guided way to learn an unfamiliar repo, and search by meaning rather than by exact name. All of it is always-on at the structural level and gets richer if you build the optional intelligence overlay.

Archetypes

A game-dev-tuned classifier auto-names each code cluster by purpose — Physics, Rendering, Shaders, Tests, Audio, ECS, Math and more — from the symbols and file paths inside it. So a subsystem reads as "Physics" instead of "cluster 7". Pure heuristic, no LLM needed; an intelligence overlay's curated layer name wins when present.

Guided tour graph_tour

An ordered "explore this codebase in N steps" walk: entry points first (where execution starts) → the major archetype regions (the big subsystems by purpose) → the hot-spots inside them → the notable cross-subsystem flows. Each step names key symbols and suggests the next verb to drill with. focus narrows it to one subsystem.

Semantic search

graph_search mode:semantic finds code by meaning — "where's the fluid pressure solve" matches even when the symbol isn't named that. Opt-in and pluggable: it embeds via any OpenAI-compatible endpoint you point it at (local Ollama or cloud) through APG_EMBED_* env. No model is bundled; with nothing configured it cleanly degrades to lexical search plus a one-line hint.

Archetypes flow into graph_overview, graph_digest, and the dashboard's "by archetype" Map mode from one shared classifier, so the agent's words and the picture stay in sync. The tour and semantic search are long-tail verbs — callable by name even though they're hidden from the focused default tool list.

5The agent front door + adaptive sizing

The single biggest lever on real usefulness isn't a new feature — it's whether the agent reaches for one verb, trusts the result, and gets an answer sized so it doesn't fall back to Read/grep. Two changes target exactly that.

🚪 One-call front door

graph_packet {target, mode} is the explicit first move — most "understand X / how does Y work" questions resolve in this one call (modes: orient / plan / debug / review / audit / verify) instead of chaining a search plus a node verb. The server-instructions playbook now names it first, and adds an honest KNOWN LIMITS block (dynamic dispatch via function-pointers / std::function / Lua callbacks, and cross-language beyond the shader bridge, are not synthesized — verify those by reading) so the agent doesn't burn calls on dead ends.

📏 Adaptive token budget

A fixed response budget starves big repos: a god-file gets truncated, the agent re-Reads it — the exact fallback we want to kill. graph_packet's budget and list caps now scale with repo size across monotonic tiers (tiny → huge, keyed on graph node count), so every cap only ever grows as the project grows. graph_explore / graph_trace were already adaptive on line budgets. Precedence: an explicit budget arg > APG_PACKET_BUDGET env > the adaptive tier.

6Freshness self-heal — a stale map is worse than none

A real field test surfaced the #1 problem: as you commit, the graph drifts behind HEAD, and a stale "not found" for a just-landed symbol is actively misleading — worse than having no graph at all, especially for managed workers who got the read verbs but couldn't refresh. The fix makes freshness discoverable, loud, and optionally automatic.

Every read warns when stale
The central gate prepends graph stale: indexed X, HEAD Y (N commits behind). Run graph_index() to refresh… — now with the commit count and the self-heal hint. A stale "not found" is explicitly not proof a symbol is gone.
always
A discoverable refresh verb
graph_index is now in the focused default tool list, so a worker reading the warning has a surfaced action to take. The reindex is incremental (diffs changed files; cosmetic-vs-structural tiers).
on demand
Opt-in auto-refresh
Set APG_AUTO_REINDEX=1 and the dispatch refreshes a behind-HEAD graph before the read handler runs — so the answer is fresh. Off by default; no behavior change unless set.
opt-in
Optional git hook
scripts/install-graph-hook.mjs installs a non-blocking post-commit reindex hook for teams that want the graph always fresh without per-read latency. Idempotent — replaces only its own block, never clobbers an existing hook.

7What's borrowed from what — and how it's used

This isn't built from scratch, and it isn't a copy-paste of any one tool. Four mature projects each solved part of the problem well; this merges their ideas into one coherent system. Three are MIT (reused with attribution; reimplemented in our JS+SQLite shapes). One is unlicensed — patterns only, no code copied.

CG

codegraph

MIT · TypeScript · the static-graph & agent-UX donor
  • C++ resolution heuristics — receiver-type inference (obj->method() → the declared type's method), out-of-line Foo::bar matching, include-dir discovery.
  • Adaptive output — size the answer to the question, skeletonize redundant siblings instead of truncating.
  • Adaptive response sizing — codegraph's measured biggest win: graph_packet's budget + caps now scale with repo size on monotonic tiers (caps never shrink as the repo grows), so big projects stop getting truncated answers.
  • The agent-eval mindset — judge the tool by how an agent behaves with vs without it (route to the right verb, trust the answer, not re-Read). It shaped the front-door + adaptive-sizing pass.
  • Generated-file down-ranking — protobuf/moc/*_generated.h rank last so a hand-written symbol wins.
  • graph_trace / graph_explore — from→to call paths with inlined bodies; multi-symbol source bundles. "Treat this as already Read."
  • The "low-salience wall" doctrine — agents under-pick from big tool lists; enrich the verbs they already call rather than adding names. Shaped our whole tool-surface design.
  • MCP initialize server-instructions — the one channel that reaches every host's prompt.
Reimplemented in JS (their TS type-shapes differ). The trace/explore verbs and the gating philosophy are the biggest lifts.

graphify

MIT · Python · the analysis & "self-describing" donor

  • God-nodes / communities / cycles — the analytics behind graph_hotspots, graph_overview, graph_cycles.
  • Archetype auto-naming — from graphify's SECTION_ARCHETYPES: name a cluster by purpose ("Physics", "Rendering", "Shaders") from its symbols + paths, so subsystems read by meaning. Powers the dashboard's "by archetype" Map mode.
  • Analysis-as-a-verb pattern — the same shared module backs both the agent verbs and the dashboard, so they never drift.
  • Safety hardening — sanitize_label against prompt-injection through indexed source; pre-parse file-size caps; SSRF guards.
  • IDF search ranking — rare identifiers outrank common ones.
Pure graph algorithms — ported cleanly. The "give the agent the dashboard's value as text" idea is graphify's signature contribution here.

understand-anything

MIT · JS/TS · the import-resolution & dashboard donor

  • Dashboard overview→drill-in — show ~8–30 cluster boxes, not 13k nodes; expand one cluster on demand. The legibility idea behind our new overview view.
  • Change-explain — our graph_explain_diff: keyed on a git diff → changed → affected → risk (the reverse of "what breaks if I touch X").
  • Non-ASCII enumeration & structural fingerprints — git ls-files -z; body-vs-signature change classification.

  • Embedding semantic search — find code by meaning via embeddings: our opt-in, pluggable graph_search mode:semantic (any OpenAI-compatible endpoint; degrades to lexical).

8How an agent actually uses it

A typical "I'm about to change this function" flow (C++, TypeScript, or Python — the verbs pick the language server by file extension). Notice it escalates from cheap-and-static to verified-and-precise, and stops the moment it has a trustworthy answer.

Orient — graph_digest for the lay of the land (subsystems, hot-spots, cycles), or graph_packet for one feature/symbol. ~1–2k tokens, no compiler needed.
Locate — graph_search / graph_whereis to find the symbol. If the index is stale it says so, so "not found" is never mistaken for "doesn't exist."
Get ground truth — graph_collect_code_intel warms the language server (clangd / tsserver / pyright) on the relevant files, turning callers into LSP_VERIFIED edges. First run is slow then cached; returns a compact summary, not a data dump.
Verify — graph_callers now shows [lsp✓] callers with a TRUST banner; code_intel_hierarchy walks the transitive call/override tree. An empty result is honestly labeled, never a false "safe to delete."
Understand the change — graph_trace from→to inlines the call path; graph_explore bundles several symbols' source; graph_explain_diff scores the blast radius of a diff. Source comes back "already-Read," so the agent stops opening files.

9The rebuilt dashboard

A live HTTP view of the same graph the agents query — for humans who want to see the codebase. The old viz dumped every node at once; the rebuilt dashboard leads with a navigable group-box Map: labeled boxes you drill into instead of a hairball. It launches on a local port (bound to 127.0.0.1) via the graph_dashboard verb.

The Map — labeled boxes you drill into

Start at a handful of group boxes, not thousands of nodes. Double-click a box (or its ⊕) to expand only it; double-click a node to focus its group. Three grouping modes change what a box means:

by directory

Boxes = folders (depth-adjustable). The structural layout — a whole folder collapses into one box you can drill into.

by community

Boxes = the graph's detected clusters (Leiden communities), each labeled with its archetype name or dominant directory.

by archetype

Merges every community of the same purpose into one of ~15 named boxes — Physics, Rendering, Shaders, Tests, Audio, ECS… The "what is this for" view.

Views, dimensions, and tools

Five view modes

Map (grouped boxes), Tree and Flow (dagre hierarchies), Force (ungrouped physics layout), and Shader (the C++↔GLSL bridge subgraph on its own).

2D + 3D

Cytoscape in 2D; a 3D force-graph with a custom clustering force that pulls each node toward its group centroid, so the boxes hold together in space. (3D adds a Layers view.)

Search → focus

Type-ahead over symbols, files, and features; pick a result to focus that node and its neighborhood.

Blast-radius

Toggle blast mode, pick a symbol → everything it reaches lights up, the rest fades. The visual twin of graph_impact.

Pathfinder

Shortest path between two symbols — how does A end up reaching B.

Provenance + shader map

Compiler-verified edges read differently from heuristic ones; node detail shows trust and shader bindings — the CPU↔GPU seam no generic tool shows.

The analysis behind the picture — clusters, archetypes, hotspots, provenance, shader map — is the same shared module the agents query, so the dashboard and the agent answers can never disagree.
