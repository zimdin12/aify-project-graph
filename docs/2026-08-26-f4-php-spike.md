# F4 — the PHP spike, and why it does not earn a backend yet

PHP is one of Steven's priority languages and the only one of them that can never earn `[lsp✓]`,
never return `exhaustive: true`, and never license an absence claim. This is the bounded spike that
was supposed to decide whether to fix that.

**Outcome: it does not earn a backend. Q1 fails on licensing, and the remaining decision is Steven's.**

## Preregistered

> **Q1.** Is a PHP language server obtainable in this environment at all?
> **Q2.** Does the existing backend registry accommodate it without structural change?
> **Q3.** Does it produce `LSP_VERIFIED` edges on fast-route?
> **Abandon rule:** if Q1 or Q2 fails, stop and report a measured blocker — do **not** build a PHP
> backend on speculation.

## Q1 — NO, and for two independent reasons

**There is no PHP runtime on this machine.** That alone eliminates every PHP-*implemented* language
server: phpactor, Psalm's language server, Serenata, and felixfbecker's `php-language-server`. None
can run here without the host installing PHP first.

That leaves exactly one credible Node-implemented server, **intelephense** — and its npm `license`
field is `SEE LICENSE IN LICENSE.txt`, not an OSI identifier. Read rather than inferred from the
field:

> **3. INTENDED USE.** An individual end user may use the Software paired with a Language Server
> Protocol compatible Integrated Development Environment or text editor to provide PHP code
> intelligence for said user.
>
> **5. RESTRICTIONS.** You are NOT permitted to: … (c) Reproduce, copy, **distribute**, resell or
> otherwise use the whole or any part of the Software for any purpose except where permitted by
> item 3 INTENDED USE.

⛔ **This project provisions its language servers by bundling them as npm dependencies** — the
module header says so outright: *"TS/Python servers are bundled npm deps resolved via
resolveNodeBin … so the host needs no LSP config."* Bundling intelephense and shipping it is
distribution, and this tool is not an IDE or text editor.

⇒ **The bundled model that works for pyright and typescript-language-server is not available for
PHP.** That is a licence fact, not a preference, and not mine to decide around.

## Q2 — YES, structurally free

A backend is a four-field descriptor, and the registry has no PHP-shaped gap to fill:

    getBackend('php')     ->  null            POSITIVE CONTROL: getBackend('python') -> BACKEND
    getBackend('PHP')     ->  null            (normalizes to 'php', still unregistered)
    inferLanguage('src/FastRoute.php') -> null

Adding one would be two lines — a `BACKENDS` entry and a `.php` extension mapping. And crucially,
**it would need no bundled dependency**, because `nodeLspSpawn` already falls through to PATH:

    nodeLspSpawn({ pkgName: 'intelephense', … })  ->  { command: "intelephense", args: ["--stdio"] }
    POSITIVE CONTROL (pyright, bundled)           ->  node …/node_modules/pyright/langserver.index.js

The two resolutions are visibly different, which is what makes the first one meaningful: an
unbundled server degrades to a bare PATH name rather than silently resolving to something else.

⇒ That is the **clangd model** this repo already uses for C++ — detect-or-guide, never distribute.

## Q3 — deliberately unanswered

Measuring whether intelephense produces verified edges on fast-route requires **running it inside
this tool**, which is the use §3 describes as an individual end user pairing it with an IDE or text
editor. Whether that covers a code-intelligence server is a licensing judgement, and it is Steven's
to make, not mine to assume by running the experiment and reporting the number.

⚠ **So this spike stops one question short on purpose.** Producing the Q3 number would have required
committing to the interpretation the number was meant to inform.

## The decision for Steven

Two viable paths, both needing his call because both are licence questions:

1. **Detect-or-guide (the clangd model).** Register a PHP backend that resolves intelephense from
   PATH only. We never distribute it; the operator installs it under their own licence, which is
   what §3 contemplates. Cost: ~2 lines plus a guide message. ⚠ **Risk: we cannot test the working
   path**, so it would ship unverified — and this repo's own rule is that a remedy that cannot work
   is worse than naming the limit.
2. **Bundle under a purchased licence.** Requires reading §4's business tiers against how this tool
   is distributed. Spends money and changes what ships.

⛔ **Doing nothing is also honest, and is what is shipped today.** `graph_health` on the PHP arm
already reports the limit accurately and refuses to suggest a remedy that cannot help:

    capabilities: { reason: "no_language_server", compilerVerifiedEdges: 0, orientationUsable: true }
    nextAction:   "no language server for php — caller sets here are heuristic permanently;
                   verify with rg before any delete or rename"

That message stays **unchanged** by this spike. Changing it to suggest installing a server would
name a remedy the tool cannot currently use — the exact defect F1 fixed.

## What this cost, and what it bought

No code changed. The spike consumed one `npm pack` into a scratch directory (never installed into
the project) and four executed probes with positive controls.

It bought a decision that was previously being deferred on a guess: **F4 is blocked on a licence,
not on engineering.** The engineering is two lines.
