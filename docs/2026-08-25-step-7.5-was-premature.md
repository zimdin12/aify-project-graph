# Step 7.5 was premature — I built before measuring whether it could ever be used

**Self-assessment, recorded so the next decision about this code is evidence-based rather than
sentimental about work already done.**

## What happened

Review refused step 8 (deleting `degraded` / `operationallyDegraded`) until a negotiated contract
boundary existed. I built it: `acceptEvidenceContractVersion`, one owner across both verbs, 25
tests, five mutants killed. It works.

Then review handed over the threshold that licenses the default flip — the thing the whole
mechanism exists to enable — and only THEN did I measure the population it applies to:

    every graph-verb caller on this machine, ever
      this repo                27 calls
      echoes-of-the-fallen    206 calls
      sand-castle              87 calls
      six other project dirs     0 calls
    controls: positive 62,773 · negative 0 · same pass

    the bar needs:  >= 5 distinct installations, >= 2 runtime families,
                    100 explicit v2 requests over 30 days
    reality:        3 callers, 2 external, ONE machine, ONE runtime family

## The error is the ORDER, not the code

Measuring the population took about five minutes. Building the mechanism took hours. Had the
measurement come first, the right move was obvious and was already written down as review's own
fallback: never flip the default, keep v1 indefinitely, add versioned v2 endpoints if a consumer
ever asks. No negotiation boundary needed.

⛔ **And this repository already contained the counter-example, three days old.**
`docs/2026-08-22-hook-fire-rate.md` measured a hook's fire rate BEFORE the hook was written, and
that measurement killed rule A at 85.5% for the cost of a script. I had that pattern in hand and
applied it to someone else's feature, not my own.

⇒ **Measure whether a thing can be reached or used BEFORE building it, not after.** This is the
same discipline as checking reachability before a quality push — applied one step earlier, to the
decision to build at all.

## ⚠ A CORRECTION TO MY OWN CLAIM

I reported the threshold as one that "will never be met". That overstates it. The accurate statement
is that it **cannot be met at current adoption** — three callers on one machine — and nothing
currently planned changes adoption by the required factor of five. It is deferred indefinitely, not
impossible. A threshold that a growing project could eventually clear is not the same as an
unreachable one, and I should not have collapsed the two.

## What is NOT being done about it

**The code stays.** Deleting working, tested code to undo a process error would be a second
unmeasured decision, and removing the schema fields alone would be worse than either option — the
mechanism would still exist while becoming unreachable from outside, which is the precise defect
this project spent the day removing five instances of.

**What stops is investment.** No telemetry apparatus. No step 8. No further work on the migration
until a consumer exists or review rules on retiring the flip.

⇒ The mechanism is DORMANT, not active: implemented, reachable, correct, and used by nobody. That is
recorded here so nobody later mistakes its passing tests for evidence that it is wanted.
